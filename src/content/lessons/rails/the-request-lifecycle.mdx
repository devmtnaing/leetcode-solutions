Rails is often taught as "routes, controllers, views", which leaves out
everything that runs *around* your code. When a request behaves strangely, the
cause is usually in that surrounding machinery — so it helps to know its shape.

## The path a request takes

1. **The web server** (Puma) accepts the TCP connection and parses HTTP.
2. It builds a **Rack env** — a plain hash of the request: method, path, headers, body.
3. That hash enters the **middleware stack**, one layer at a time.
4. The router matches the path against `config/routes.rb` and picks a controller and action.
5. Rails instantiates the controller — **a new object per request**, never reused.
6. **Before-actions** run, in the order declared.
7. Your action runs.
8. The view renders, usually into a string of HTML.
9. The response unwinds back out through every middleware layer it came in through.

Run `bin/rails middleware` in any app and you get the real stack for step 3. It
is longer than most people expect, and reading it once explains a lot.

## Where bugs actually live

**Middleware ordering.** The stack is symmetric: a request goes down and the
response comes back up. A layer added in the wrong place sees the request before
the session exists, or after the response has already been committed. If
something you set is mysteriously absent, check whether your code runs above or
below the layer that provides it.

**Before-action ordering.** `before_action :authenticate` declared *after*
`before_action :load_record` means you load the record for people who aren't
logged in yet. That's not a hypothetical — it is one of the more common
authorization holes in Rails apps, and it's invisible unless you read the
callbacks in order.

## The one habit worth building

When behaviour surprises you, ask *which step* it came from before you ask what
the code does. "The param isn't there" has a different answer at step 3 than at
step 7. Nearly all of Rails' magic is just code running at a step you weren't
thinking about.
