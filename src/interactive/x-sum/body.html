The problem

quoted from LeetCode

You are given an array nums of n integers and two integers k and x.

The x-sum of an array is calculated by the following procedure:

  1. Count the occurrences of all elements in the array.
  2. Keep only the occurrences of the top x most frequent elements. If two elements have the same number of occurrences, the element with the bigger value is considered more frequent.
  3. Calculate the sum of the resulting array.

Note that if an array has less than x distinct elements, its x-sum is the sum of the array.

Return an integer array answer of length n - k + 1 where answer[i] is the x-sum of the subarray nums[i..i + k - 1].

3318 n ≤ 50 · values ≤ 50 3321 n ≤ 10⁵ · values ≤ 10⁹ 1 ≤ x ≤ k ≤ n

0X-SUM

Example 1

Input nums = [1,1,2,2,3,4,2,3], k = 6, x = 2

Output [6,10,12]

  • [1,1,2,2,3,4] keeps 1 and 2 → 1+1+2+2 = 6
  • [1,2,2,3,4,2] keeps 2 and 4 → 2+2+2+4 = 10. 4 survives because it beats 3 and 1, which occur the same number of times.
  • [2,2,3,4,2,3] keeps 2 and 3 → 2+2+2+3+3 = 12

Example 2

Input nums = [3,8,7,8,7,5], k = 2, x = 2

Output [11,15,15,15,12]

  • Here k == x, so a window can never hold more than x distinct values and nothing is ever dropped.
  • Every answer is just the sum of the window: 3+8, 8+7, 7+8, 8+7, 7+5.
  • A good sanity check — if your code disagrees here, the "fewer than x distinct" rule is wrong.
Three ways the statement bites — worth reading before you code
  • "More frequent" means (count, then value). Rank by count alone on Example 1 and you get [6,7,12] — the first window still passes, so the bug hides until the second.
  • Fewer than x distinct values is not an error. Nothing is dropped and the x-sum is the whole window, as in Example 2.
  • On 3321 the sums need 64 bits. k × max value reaches 5×1013, well past a 32-bit int — this bites in C++, Java and Rust, though Go's int is already 64-bit.

Three questions the sliding window raises

Why lift the card off the shelf before changing its count?

A card's position on a shelf is its rank, and its rank is its count. Bump the count first and the card is filed under a key it no longer has — the binary search looks in the new spot, misses, and both shelves quietly rot.

Why does the updated card always go back to REST?

Because then rebalance is the only function that knows the invariant, so it is the only place that can break it. No branching on whether the card outranks anything — drop it in the cheap place and let one function sort it out.

Can the swap loop ping-pong forever?

No. It only runs when up > down, and up is still sitting in REST after the demote, so the promoted card is never the one just dropped. Each swap strictly raises TOP's rank sum, so it terminates — in practice after one pass.
